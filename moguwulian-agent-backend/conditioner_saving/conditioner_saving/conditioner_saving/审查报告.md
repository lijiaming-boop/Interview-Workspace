## 主要问题

### 1. [P0] 生产认证链路既未闭环，又可被绕过

[docker-compose.yml](E:\\contion simulation\\conditioner_saving\\conditioner_saving\\conditioner_saving\\docker-compose.yml) 设置了 `REQUIRE_AUTH=true`，但：

- 没有部署 Go 认证代理。
- Next.js 只做透明转发，不生成身份头。
- `AUTH_SECRET` 默认空值。
- 空密钥时，攻击者可自行提交 `X-User-Info` 并伪造 `admin` 角色；已通过最小复现验证。
- 配置密钥后，正常前端请求又会因为没有签名组件而全部返回 401。

即使接入现有 Go 代理也不安全：[proxy/main.go](E:\\contion simulation\\conditioner_saving\\conditioner_saving\\conditioner_saving\\proxy\\main.go) 从可由浏览器修改的 `user_info` Cookie 读取身份，再为其生成 HMAC，相当于给攻击者伪造的身份“盖章”。

### 2. [P0] 上传内容仍可触发高权限 Agent

确定性技能改成直接运行受控脚本是明显进步，但 [skill_caller.py](E:\\contion simulation\\conditioner_saving\\conditioner_saving\\conditioner_saving\\core\\skill_caller.py) 仍允许：

- 空压提取 Agent 使用 `Read + Write` 和 `bypassPermissions`，可能读取密钥或覆盖项目文件。
- 仿真 Agent 使用 `Read + Write + Bash`，并在项目根目录执行。
- 拓扑、工况等内容来自用户输入，提示词注入风险仍然存在。

这部分必须使用无密钥、无宿主目录、默认无网络的独立沙箱；空压提取应让模型只返回 Schema 校验后的 JSON，由服务端负责写文件。

### 3. [P1] 相似案例接口仍泄露其他用户数据

`/history` 已增加用户过滤，但 [similar_cases](E:\\contion simulation\\conditioner_saving\\conditioner_saving\\conditioner_saving\\apps\\api\\routers.py) 仍从全局历史库读取并返回其他用户的：

- `session_id`
- `user_id`
- 原始文件名
- 项目地区和节能率

普通用户只能搜索自己的案例；跨用户案例只能提供给特权角色，或返回彻底脱敏的统计数据。

### 4. [P1] 数据库任务锁不是安全租约

[claim_task/release_task](E:\\contion simulation\\conditioner_saving\\conditioner_saving\\conditioner_saving\\apps\\api\\storage.py) 存在：

- 查询后插入/更新不是原子操作。
- 两个进程可同时抢占陈旧锁并都返回成功。
- 释放锁时不检查 owner。
- 旧任务超时后，新任务接管；旧任务结束时会把新任务的锁删除。
- 没有续租心跳，超过一小时的合法任务会被误抢占。
- Agent 先创建 `running` 记录再抢锁，抢锁失败会留下幽灵运行记录。

建议使用唯一 lease token、条件更新、按 token 删除，并定期续租；PostgreSQL 环境也可使用 advisory lock。

### 5. [P1] Agent Token 用量会被重复累计

每个步骤已经在 `add_step()` 中累计数据库用量，但 [_finalize_run](E:\\contion simulation\\conditioner_saving\\conditioner_saving\\conditioner_saving\\apps\\api\\agent_service.py) 又把数据库用量和本轮 trace 用量相加。

结果是：

- 新任务用量约被计算两次。
- 恢复任务会再次叠加本轮用量。
- 预算、费用和审计数据全部失真。

### 6. [P1] 后端接口改了，前端没有同步

当前后端已经：

- 拒绝 `.xls`。
- 删除完整计算表的密码参数，改为角色授权。

但前端仍允许选择 `.xls`，并继续显示密码框、发送明文密码、把 403 显示成“密码错误”，见 [Workflow.tsx](E:\\contion simulation\\conditioner_saving\\conditioner_saving\\conditioner_saving\\apps\\web\\src\\components\\Workflow.tsx) 和 [下载区](E:\\contion simulation\\conditioner_saving\\conditioner_saving\\conditioner_saving\\apps\\web\\src\\components\\Workflow.tsx)。

### 7. [P1] 新增覆盖率指标存在单位错误

`expected_rate` 使用百分数，例如 `11.9`；区间端点使用小数，例如 `0.086～0.131`。但 [interval_covers](E:\\contion simulation\\conditioner_saving\\conditioner_saving\\conditioner_saving\\evaluation\\metrics.py) 直接比较二者。

因此报告显示覆盖率 0%，实际上 `patchy` 的 11.9% 明明落在 8.6%～13.1% 内。最小复现也得到 `expected True, actual False`。

## 其他需要修正

- [DataFiller](E:\\contion simulation\\conditioner_saving\\conditioner_saving\\conditioner_saving\\core\\data_filler.py) 的 `filled_count` 同时统计月度字段和顶层 `electricity_price`，但完整率分母只统计月度可用字段，可能导致原始完整率偏低甚至为负数。应拆分 `monthly_filled_count` 和总填充数量。
- [确定性脚本超时](E:\\contion simulation\\conditioner_saving\\conditioner_saving\\conditioner_saving\\core\\skill_caller.py) 实际无效：代码先阻塞遍历 stdout，只有进程退出后才调用带 timeout 的 `wait()`。脚本挂死时线程和任务锁会永久占用。
- [XLSX 验证](E:\\contion simulation\\conditioner_saving\\conditioner_saving\\conditioner_saving\\apps\\api\\upload_guard.py) 只检查 `PK\x03\x04` 四字节；测试甚至使用伪 ZIP 数据并成功上传。需要验证 ZIP 目录、`[Content_Types].xml`、工作簿入口、成员数量、单成员大小和总解压大小，防止伪文件及 ZIP 炸弹。
- [密钥扫描器](E:\\contion simulation\\conditioner_saving\\conditioner_saving\\conditioner_saving\\scripts\\scan_secrets.py) 明确跳过 `.env`，所以即使有人强制把 `.env` 加入 Git，CI 也检测不到；同时 `.dockerignore` 没有排除 `.env`，密钥会进入 Docker 构建上下文。扫描器应基于 `git ls-files` 扫描所有受版本控制文件。
