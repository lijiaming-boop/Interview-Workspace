**原因**: 这是业务逻辑,不是技术实现
- 节能率计算公式是业务规则

**原因**: 这是数据定义,不是技术实现

**原因**: 这是质量约束,不是技术实现
- 性能要求(≤30秒、≤10秒)

## 职责边界

| 维度 | PRD | 技术方案 |
|------|-----|----------|
| 核心问题 | 做什么 & 为什么 | 怎么做 |
| 技术选型 | ❌ 不写 | ✅ 详细写 |
| 架构设计 | ❌ 不写 | ✅ 详细写 |
| 业务逻辑 | ✅ 详细写 | ✅ 实现 |
| 数据定义 | ✅ 详细写 | ✅ 基于此设计 |
| 性能指标 | ✅ 写约束 | ✅ 写方案 |

## 判断标准

当犹豫某内容该不该写进PRD时:

**问题**: 如果技术用另一种实现方式,是否会影响用户体验或业务结果?

- **会影响** → 可以写(作为约束)
- **不会影响** → 不该写(交给技术)

## 示例

### ✅ 可以写
- "数据上传后30秒内完成处理" (性能约束)
- "支持5-10人并发访问" (并发约束)
- "节能率偏差≤2%" (准确性约束)

### ❌ 不该写
- "使用Streamlit框架" (技术选型)
- "用pandas处理数据" (实现方式)
- "session state管理状态" (技术细节)

## 经验总结

### 关键教训
1. **PRD不是技术文档**: PRD定义"要什么",技术方案定义"怎么做"
2. **业务逻辑≠技术实现**: 节能率计算公式(业务逻辑)应该在PRD,但用什么库实现(技术选型)不应该在PRD
3. **约束≠选型**: "需要处理Excel文件"是约束(可以写),"用pandas处理Excel"是选型(不该写)

### 判断技巧
遇到任何内容,问自己:
- 如果换一种技术栈(如Java + Spring代替Python + Streamlit),这个内容是否需要改变?
- 如果需要改变 → 技术实现细节 → 不该出现在PRD
- 如果不需要改变 → 业务需求/约束 → 可以出现在PRD

### 边界案例
**第12章算法为什么保留?**
- 节能率计算公式定义了"什么是正确答案"
- 无论用什么语言实现,公式都是一样的
- 这是业务规则,不是实现细节
- 因此应该保留在PRD中

**第5章性能要求为什么保留?**
- "30秒内完成处理"是产品质量标准
- 无论什么技术栈,都必须满足这个标准
- 这是约束条件,不是实现方式
- 因此应该保留在PRD中
