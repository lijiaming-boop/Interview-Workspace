## 总体结论

这个项目已经具备较完整的业务闭环和不错的工程原型，但当前定位应是“内部试点/验证版”，还不适合直接作为生产系统上线，也不宜对外承诺“节能率误差 ≤2%”。

| 维度               | 评价 | 判断                                      |
| ------------------ | ---: | ----------------------------------------- |
| 业务价值与产品方向 | 8/10 | 痛点明确，AI 与 Excel 计算引擎结合合理    |
| 工程原型完整度     | 7/10 | 前后端、Agent、仿真、报价、评估链路较齐全 |
| 计算结果可信度     | 5/10 | 有确定性公式，但当前回归样本和精度不足    |
| 安全与生产就绪度   | 3/10 | 存在文件、权限、密钥和任意命令执行风险    |
| 可维护性           | 5/10 | 新旧架构共存、模块过大、重复实现较多      |

本次分析按“业务链路—代码证据—动态验证—改进优先级”的方式进行，不仅依据文档描述，也实际运行了测试、构建和回归评估。分析过程中没有修改项目代码，工作区保持干净。

## 一、项目当前实际形态

项目现在并不是单一架构，而是三套流程并存：

```text
旧 Streamlit 流程
        │
        ├── Next.js 分阶段流程：首页仍在使用
用户 ──┤      上传 → 提取 → 填充 → 计算
        │
        └── Agent 编排流程：位于独立 /agent 页面
                    ↓
          Python脚本 / LLM Skill / Excel公式
                    ↓
              结果、仿真、报价
```

README 重点宣传 Agent 化工作流，但首页实际上仍加载固定阶段的 [Workflow.tsx](<./apps/web/src/components/Workflow.tsx:58>)，入口见 [page.tsx](<./apps/web/src/app/page.tsx:15>)。Agent 只是独立功能，没有真正取代主流程。

这会造成：

- 用户体验和产品宣传不一致。
- 相同业务逻辑在多处实现。
- 修复一个流程后，其他流程可能继续保留旧问题。
- 测试、部署和运维成本持续增加。

## 二、项目做得比较好的地方

- 将“AI 判断”与“Excel 确定性计算”分开，整体方向正确。
- 计算失败已经改为显式报错，不再返回虚假的默认节能率。
- 具备数据质量门禁、站房类型拦截、会话隔离和回归评估机制。
- Agent 编排器具备工具白名单、步骤追踪和质量状态控制。
- 单元测试、代码检查和前端构建基础较好。

实际验证结果：

- 单元测试：270 通过、10 跳过。
- 代码规范检查：通过。
- Next.js 生产构建：通过。
- 回归评估程序：可正常运行。
- 但集成测试在收集阶段失败，原因是测试仍引用已经不存在的 `_write_chiller_to_session_state`。
- 当前 CI 没有运行集成测试、安全测试和真正的端到端流程，因此 CI 可能显示成功，但系统集成实际上已经损坏，见 [ci.yml](<./.github/workflows/ci.yml>)。

## 三、必须优先解决的 P0 问题

### 1. 文件上传和下载存在严重安全风险

多个上传接口直接使用用户提交的文件名拼接路径，虽然项目中存在 `_sanitize_filename`，但关键接口没有使用。攻击者可能通过特殊文件名把文件写到会话目录之外。仿真下载接口也没有验证最终路径是否仍在允许目录内。

证据集中在 [routers.py](<./apps/api/routers.py:225>)。

需要统一实现：

- 文件名净化和最终路径边界检查。
- 流式上传及单文件、批次总量限制。
- 文件签名、压缩炸弹和 Excel 内容验证。
- 下载文件使用服务端白名单，不接受任意文件名。
- 当前代码声明支持 `.xls`，但运行环境缺少相应读取依赖；应暂时拒绝，或增加安全转换流程。

### 2. 用户身份和数据隔离不可靠

API 信任客户端传入的 `X-User-Info`。旧代理只判断身份 Cookie 是否存在，并直接信任另一个可由浏览器修改的用户信息 Cookie，因此用户身份和角色可能被伪造，见 [proxy/main.go](<./proxy/main.go:298>)。

另外：

- 会话列表和历史记录没有按当前用户过滤。
- 仿真初始化可通过其他会话 ID 读取和复制文件。
- 全局指标对普通登录用户可见。
- Docker 部署直接暴露 API，绕过代理更加容易，见 [docker-compose.yml](<./docker-compose.yml>)。

建议改为同源网关/BFF，并由后端验证 OIDC/JWT；所有资源接口都必须同时检查“角色”和“资源所有权”。

### 3. 上传文件可能间接触发任意命令执行

主流程的 Skill 调用给 Agent 开放了 `Bash`、`Write`，并使用 `bypassPermissions`。上传的 Excel 内容和文件名又会进入提示词。如果恶意内容诱导 Agent 执行命令，可能读取密钥、修改文件或访问其他会话数据，见 [skill_caller.py](<./core/skill_caller.py:147>)。

建议：

- 确定性提取直接调用受控 Python 脚本，不经过通用 Agent。
- LLM 只接收结构化数据，只返回受 Schema 约束的 JSON。
- 移除 Shell 和任意文件写入权限。
- 如果必须执行生成代码，应放入无密钥、无宿主机目录、默认无网络的临时沙箱。

### 4. 已泄露密钥必须轮换

Git 历史显示曾提交过包含真实 API Key 的 `.env`，后来虽然停止跟踪，但历史中的密钥仍然存在。

应立即：

- 撤销并轮换该密钥。
- 清理 Git 历史。
- 增加提交前密钥扫描和 CI 密钥扫描。
- 不要只依赖 `.gitignore`。

### 5. 管理下载口令设计不安全

完整文件下载使用默认口令 `admin123`，且口令通过 URL 查询参数传输。这可能进入浏览器历史、代理日志和访问日志。

应删除共享口令，改为基于角色的授权或短期签名下载链接。

## 四、计算准确性是当前最大的业务阻碍

[回归报告](<./evaluation/report.md:7>)虽然显示工作流决策通过率 100%，但真正带预期节能率的样本只有 4 个：

- 误差不超过 2 个百分点：2/4，即 50%。
- 平均偏差：1.97 个百分点。
- 最大偏差：5.42 个百分点。
- 某缺夏季数据案例预期 12.1%，实际为 17.5%～21.0%。

而且当前评估方式还有三个问题：

- 数据集只有 9 个案例，其中只有 4 个有节能率真值。
- 部分预期值和地区信息来自文件名，不能算独立可靠的业务真值。
- 只要预期值落在结果区间内，偏差就记为 0；区间越宽反而越容易“准确”。

[业务口径确认单](<./docs/业务口径确认单.md:1>)也明确记录了两个差异尚未获得业务负责人认可。因此目前不应对外宣传“误差 ≤2%”。

建议建立至少 30～50 个由暖通专家签字确认的真实项目数据集，并划分：

- 公式校准集。
- 独立验证集。
- 最终盲测集。

同时评估点误差、区间覆盖率、区间宽度、不同地区/站房类型的分层误差。

## 五、代码中已经发现的结果正确性问题

### 1. 原始总能耗被错误写成总节能量

[excel_calculator.py](<./core/excel_calculator.py:397>) 中 `total_energy_original` 使用了 `total_saving`，会导致前端摘要或导出结果错误。

### 2. 能耗单位不统一

部分报价和方案代码把原始数值直接标记为“万 kWh/年”，另一些地方则执行除以 10000。建议建立统一的能量值类型和转换函数，内部统一使用 kWh，展示层再转换。

### 3. Excel 结果缺失时静默返回 0

当公式单元格不存在、公式未计算或映射失效时，当前逻辑可能返回 `0.0`。这会把计算故障伪装成“无节能效果”。

应该改为失败关闭，并增加：

- 节能率上下限顺序检查。
- 数值有限性和合理范围检查。
- 分项节能量与总节能量一致性检查。
- 节能量不得超过原始能耗。
- 公式模板版本和单元格映射版本绑定。

### 4. 数据完整率口径不统一

填充器固定使用 `12个月 × 7字段` 作为分母，但部分模板允许字段不同。这会导致提取阶段和填充后阶段对“完整率”的判断不一致。

### 5. 默认填充值缺少业务版本管理

季节代表值和行业默认值目前大多是硬编码。已知最大偏差案例也与默认填充值有关。建议为默认值增加来源、地区、气候区、设备类型、版本和适用范围，并把填充值造成的不确定性传递到最终节能率区间。

## 六、仿真目前不能作为独立验证证据

仿真 Skill 明确要求调整优化参数，使仿真节能率与前序评估目标的差异小于 1%。这本质上是“按目标调参”，不是独立验证。

建议拆成两个明确流程：

- 校准模式：允许利用目标节能率调整参数。
- 验证模式：参数冻结后，使用独立运行数据检验结果，不允许继续追目标。

并优先使用仓库中固定、可测试、可版本化的仿真引擎，避免每次由 Agent 动态生成并执行代码。

## 七、架构和可维护性改进

当前存在几个超大文件：

- `apps/api/routers.py` 约 1858 行。
- `apps/api/services.py` 约 1598 行。
- `Workflow.tsx` 约 934 行。
- Streamlit 旧入口仍有上千行代码。

建议按领域拆分为：

- 中央空调评估。
- 空压机评估。
- 仿真。
- 报价。
- Agent 编排。
- 用户与管理。
- 文件与任务基础设施。

同时需要：

- 在 Streamlit、分阶段 Web 流程和 Agent 流程中选择一个主流程。
- 合并 `core/quote` 与 `quote_module` 两套报价实现。
- 使用明确的请求模型、状态枚举和状态迁移，减少裸字典和字符串状态。
- 修复 Agent 恢复逻辑：当前恢复后可能丢失原 Brain、工具注册表和累计用量，空压机任务甚至可能按中央空调工具恢复，见 [agent_service.py](<./apps/api/agent_service.py:202>)。
- 用持久化任务队列和数据库锁替代进程内线程及任务字典，避免重启丢任务、重复执行和多实例竞争。
- 不再静默吞掉数据库写入失败。

## 九、建议设置的上线门槛

只有同时满足以下条件，才建议进入生产：

- 安全：不存在路径穿越、身份伪造、跨用户读取和上传触发命令执行。
- 准确性：独立盲测达到业务认可的误差、覆盖率和区间宽度要求。
- 稳定性：单元、集成、端到端、安全、迁移和部署测试全部通过。
- 可恢复性：进程重启、任务恢复、重复请求和多实例执行均经过验证。
- 运维：具备监控、告警、备份恢复、回滚和密钥轮换能力。

最终建议是：先把项目做成“可信的计算产品”，再扩展为“企业级 Agent 平台”。目前影响项目价值的核心不是缺少更多 AI 功能，而是安全边界、业务真值和工程一致性还没有建立起来。

团队复盘时可以用三个问题检验是否真正理解现状：

1. 为什么“流程决策通过率 100%”不代表节能率准确？
   答案要点：只有 4 个真值样本，且区间内即记零偏差。

2. 当前最危险的技术路径是什么？
   答案要点：不可信上传内容进入拥有 Shell、写文件和权限绕过能力的 Agent。

3. 为什么不应同时维护三套主流程？
   答案要点：业务规则分叉、测试覆盖失真、问题修复无法同步。
