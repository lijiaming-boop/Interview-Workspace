## 一、项目一句话

**HVAC Energy Agent**：面向暖通节能售前场景的领域 Agent——上传一份客户调研表，
Agent 在硬约束护栏内自主完成"数据提取 → 质量评估 → 缺失填充 → 物理公式测算 →
结论输出"的全流程，节能率计算偏差经回归评测验证（平均 0.82 个百分点）。

电梯稿（30 秒版）：
> 中央空调节能改造的售前测算，痛点是客户调研表数据质量差、人工测算慢且口径不统一。
> 我做了一个领域 Agent：LLM 负责理解调研表、规划测算路径、生成面向客户的结论；
> 但所有进入报价的数字都由确定性物理公式引擎算出——节能率计算交给 Excel 公式引擎
> 而不是大模型，因为精度要求是偏差 ≤2%。Agent 的自主性有明确边界：数据质量不达标
> 时它会自主中断并告诉你缺什么，而不是硬算一个不可信的结果。整条链路有完整轨迹
> 落盘，每一步的决策理由、工具观察、token 消耗都可以逐帧回放。

## 二、业务场景

### 2.1 谁在用、痛什么

| 角色 | 痛点 | Agent 怎么解 |
|---|---|---|
| 销售 AR | 拿到客户调研表后出方案要等几天 | 上传即算，分钟级出节能率区间和分项明细 |
| 解决方案 SR | 调研表数据脏（缺月、错值、"16~20"这种季节范围值），反复电话确认 | 自动质检 + 规则填充（插值/季节代表值），不达标的字段列成清单找客户要 |
| 团队管理 | 测算靠个人经验，报价口径不统一 | 物理公式固化在 Excel 模板引擎里，人人同口径；完整率<50% 强制中断，低质量数据出不了结果 |

### 2.2 四条业务线

| 业务线 | 输入 → 输出 | 智能化方式 |
|---|---|---|
| **空调节能率测算**（主线，本次 Agent 化） | 调研表 Excel → 节能率区间 + 分项节能量 + 结论摘要 | AgentOrchestrator 统一编排（`agent/`） |
| 空压机节能测算 | Excel/Word/PPT 调研表 → 节能率 + 方案 docx + 报价 xlsx | LLM 非结构化字段提取（claude-agent-sdk） |
| 冷站全年 8760h 仿真 | 调研表 + 设备铭牌照片 → 新旧站全年能耗对比 | **Agent 动态生成仿真 Python 代码**，ast 自检 + 报错自愈 |
| 标准能管报价生成 | 调研表 + 价格目录 → 双价报价表 | LLM 语义冲突检测（如客户要闭环控制但目录是标准件） |

## 三、核心架构（改造后）

```
用户上传调研表
      │
      ▼
AgentOrchestrator（ReAct 循环：决策 → 执行 → 观察 → 再决策）
      │
      ├── Brain（唯一的 LLM 成本点）
      │     ├─ LLMBrain：白名单内选工具 + JSON 强约束 + 解析失败自动重试
      │     └─ RuleBrain：零成本规则策略（评测/离线/无 Key 自动降级）
      │
      ├── 硬约束白名单（代码强制，模型绕不过）
      │     完整率<50% / unsupported 站房 / 不可填充 → 只能求助用户
      │     工具前置依赖 + 越权拒绝 + 连续失败熔断 + 步骤预算
      │
      ▼ ToolRegistry（确定性工具，执行零 token）
extract_survey → suggest_filling → apply_filling → calculate_saving_rate
      │
      ▼
formulas Excel 公式引擎（双 sheet 上下限，物理公式在模板里）
      │
      ├── agent_trace.json（轨迹落盘：决策理由/观察/耗时/token）
      └── FastAPI /agent/run (SSE 实时推送) + /agent/{id}/trace (复盘)
```

**设计哲学一句话：算得准的交给公式，看得懂的交给模型；凡是进入报价的数字，
必须来自确定性引擎。** 详见 ARCHITECTURE.md 的决策边界表。

## 四、本次改造做了什么（P1→P3）

### P1 — Agent 化核心（新增 `agent/` 包，约 1100 行 + 17 个单测）

| 改造项 | 位置 | 说明 |
|---|---|---|
| 工具注册表 | `agent/tools.py` | 4 个确定性工具 + 2 个控制工具，带 JSON Schema，执行零 LLM 成本 |
| 决策核心双实现 | `agent/brain.py` | LLMBrain（JSON 强约束 + markdown 围栏容错 + 2 次重试）/ RuleBrain（零成本策略，含填充占比>50% 转人工的风险判断） |
| ReAct 编排器 | `agent/orchestrator.py` | 白名单硬约束、门禁强制中断、熔断、事件流 |
| 轨迹记录器 | `agent/trace.py` | 每步工具/参数/理由/观察/耗时/token，增量落盘可崩溃恢复 |
| Agent 端点 | `apps/api/routers.py` | `POST /agent/run`（SSE）、`GET /agent/{id}/trace`；产物同步回 session_store，复用既有 /result、/download |
| **删除 mock 静默降级** | `core/excel_calculator.py` | 计算失败原来会返回假节能率（`"mock": true`）给前端报价——现在显式报错。历史上因此出过"前端展示假数据"事故 |
| token 可计量 | `core/llm_client.py` | 新增 `create_message_with_usage`；并修复 SSL_CERT_FILE 坏路径导致的直连崩溃 |

### P2 — 回归评测（新增 `evaluation/` 包）

- 评测集：6 份**文件名自带预期节能率锚点**的标注样例调研表（业务方遗留资产，如
  `【齐全】15.2%惠州光弘`）。
- 指标：流程决策正确率、节能率与锚点偏差（≤2pp 达标）、低质量数据中断正确率、
  地区识别正确率。
- 支持基线固化与回归比对（`--save-baseline` / `--compare-baseline`）。
- **评测运行全程零 LLM 成本**（RuleBrain 驱动），结果逐字节可复现。

## 六、技术亮点清单（答辩可讲的 8 个点，附代码位置）

1. **Agent 自主编排 + 硬约束护栏**：白名单机制让"自主性有边界"可被代码证明——
   `agent/orchestrator.py::_allowed_tools`。越权调用会被拒绝并写进轨迹（有测试证明）。
2. **成本分层**：确定性工具零 token，LLM 只在决策点——把"跑个脚本也要开 agent 会话"
   的旧架构改成了 tool-calling，一次测算成本从每阶段一个会话降到 ~3.5k tokens。
3. **双 Brain 降级设计**：LLMBrain/RuleBrain 同一接口，无 Key/离线/评测自动降级，
   评测因此零成本可复现——`agent/brain.py`。
4. **JSON 强约束决策**：markdown 围栏剥离、包围文本容错、失败带错误反馈重试——
   `agent/brain.py::LLMBrain._parse_decision`（5 个专项单测）。
5. **Agent 动态写仿真代码**（既有亮点，重点讲）：冷站 8760h 仿真的 Python 代码由
   agent 现场生成，`ast.parse` 自检，执行失败把报错喂回去自愈——`.claude/skills/plant-simulation/`。
6. **完整轨迹可观测**：每步决策理由/观察/token 落盘 `agent_trace.json`，
   `/agent/{id}/trace` 直接回放——答辩时逐帧讲一条真实轨迹。
7. **质量门禁即产品逻辑**：完整率<50% 或含热水泵/蓄冷/中低温机组时 Agent 拒绝出数，
   列清单找用户要数据——"知道自己不知道"是和玩具 demo 的分界线。
8. **锚点式回归评测**：用业务方标注的预期节能率文件名做天然评测锚点，已知缺口
   （模板变体）标记 known_gap 并给根因，不藏分。

## 七、5 分钟演示脚本

1. **(30s) 讲业务**：AR/SR 协作痛点 → 上传一份"缺冬季数据"的真实调研表。
2. **(1min) Agent 模式跑完**：`POST /api/agent/run?mode=auto`，SSE 里看 agent 逐步
   叙事（"当前完整度 0.75，文件名提示缺冬季，先生成填充建议判断能否继续…"）。
3. **(1min) 逐帧回放轨迹**：`GET /api/agent/{id}/trace`——每步的工具、参数、观察、
   token；指出 llm_usage 合计 ~3.5k tokens。
4. **(1min) 讲边界**：换一份"数据缺失过多"的表 → Agent 中断并列出缺失项；
   换含热水泵的表 → unsupported 拦截。强调：这些拦截是代码强制的，模型绕不过。
5. **(1min) 展示零成本模式**：`mode=deterministic` 再跑一遍，结果一致、token 为 0；
   顺带跑 `python -m evaluation.run_eval` 展示评测报告。
6. **(30s) 收尾**：冷站仿真模块里 agent 现场写仿真代码的录屏/轨迹（加分项）。

## 八、答辩 Q&A 预案

**Q1：为什么不把节能率计算也交给 LLM？**
报价场景精度要求 ≤2%，LLM 算数不可信。物理公式（COP、泵相似定律频率^2.5）由
领域专家维护在 Excel 模板里，用 formulas 库确定性执行。LLM 负责它擅长的：理解
脏数据、规划流程、生成人话。

**Q2：你这个"Agent"和普通的"调 API 的脚本"区别是什么？**
三个可验证的区别：① 决策与执行分离——Brain 在白名单内自主选择工具，而不是
写死的 if-else（但白名单保证了安全性）；② 观察驱动——每步工具的返回会进入下一
次决策的状态，异常路径（门禁/熔断/求助）都是模型根据观察做出的；③ 全程轨迹可
回放、token 可计量，行为可审计。

**Q3：怎么保证 LLM 不瞎选工具搞坏数据？**
白名单越权直接拒绝并作为观察反馈（有单测）；填充工具只写 null 字段且保护字段
（地区/站房类型）不可改写；计算失败显式报错（我们删掉了 mock 兜底），绝不给前端
假数。

**Q4：评测给你带来过什么实际收益？**
三次真实收益：① 它暴露了"月份表头被误读成能耗"的静默错数 bug——错误值
1,2,3 会被当真数据流入计算，比报错危险得多；② 它定位了深度调研模板变体被
门禁误拦的三层原因（提取关键词不匹配→完整率分母含模板没有的字段→建议引擎
把模板缺席字段判为不可填充），修复后决策正确率 6/6；③ 它量化了行业默认值
填充的口径代价（该用例偏差 5.42pp），为参数校准排出优先级。

**Q5：成本怎么样？**
一次完整测算 5 次决策调用约 3.5k tokens；评测模式 0 成本。改造前每个阶段（包括
纯规则脚本环节）都要起完整 agent 会话——这是本次架构改造省下来的。

## 十、复现指引

```bash
# 单元测试（agent 核心 16 个）
pytest tests/unit/test_agent_orchestrator.py -v

# 回归评测（零 LLM 成本）
python -m evaluation.run_eval
python -m evaluation.run_eval --compare-baseline

# 端到端（需 .env 配好 LLM；不配则自动降级确定性模式）
uvicorn apps.api.main:app --port 8000
curl -X POST "localhost:8000/api/upload?module_type=air_conditioner" -F "file=@调研表.xlsx"
curl -X POST "localhost:8000/api/agent/run/<session_id>?mode=auto"
# 轨迹回放
curl "localhost:8000/api/agent/<session_id>/trace"
```
