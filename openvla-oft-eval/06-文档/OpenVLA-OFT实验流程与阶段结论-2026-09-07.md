# OpenVLA-OFT 实验流程、阶段成果与问题闭环

> 更新日期：2026-09-07  
> 适用范围：迁移后的当前云端 GPU 实例及本轮可复现实验  
> 权威口径：以当前实例重新运行得到的日志、动作轨迹和接触记录为准  
> 历史边界：迁移前的 495/500、旧 state 29 确定性失败等记录只作背景参考，不作为当前模型对比结论

## 一、执行摘要

本阶段已经完成云端环境恢复、LIBERO 导入、官方专家数据下载与结构校验、HDF5 到 TFDS/RLDS 转换、全量 LoRA 微调、head-only 微调、严格同任务成功率对照、动作轨迹对比及 MuJoCo 接触分析。

当前最可靠的结论如下：

1. **当前权威模型仍是未追加本轮微调的 OpenVLA-OFT LIBERO-Spatial 基座模型。** 在 top drawer 任务的 50 个初始状态上，基座为 **48/50（96%）**。
2. **本轮两种 head-only 配置均未提升基座。** 使用单任务自定义统计量时为 **41/50（82%）**；使用基座统计量时为 **37/50（74%）**。
3. **全量 LoRA 也没有得到可用改进。** 单任务 50 条官方专家轨迹、rank 32、500 steps 的模型在定向状态评估中失败；Step 250、Step 500、统计量切换及夹爪符号试验均未证明有效。
4. **专家 HDF5 文件本身结构完整，不能简单判定为“坏数据”。** 目标文件包含 50 条轨迹、7479 个 transition、双路 RGB、8 维 proprio 和 7 维动作，位置与旋转维度均有变化。当前风险主要在数据覆盖、转换语义、时间对齐及训练配方，而不是文件损坏。
5. **上游视觉/语言编码器不是本轮 head-only 退化的直接来源。** 同一输入下基座与 head-only 模型的上游 hidden state 完全一致，差异集中在 action head。
6. **“只要碰到抽屉就会失败”已被否定。** 基座成功轨迹也会在碰碗前短暂接触柜体；真正差异是 head-only 的接近轨迹、接触时序、抓取几何和后续抬升过程发生偏移。
7. 当前尚未完成的是夹爪闭合、左右夹指接触、双指包络、碗抬升和末端轨迹的同步记录。第一版检测器生成了空记录，第二版修复过程中出现终端退出，尚需完成单组冒烟验证。

本轮主要比较对象：

## 三、实验流程

### 3.1 云端环境恢复

在迁移后的 DSW GPU 实例上重新建立运行环境：

- Python 3.10 虚拟环境：`/mnt/workspace/venv_oft`；
- OpenVLA-OFT：`/mnt/workspace/openvla-oft`；
- LIBERO：`/mnt/workspace/LIBERO`；
- 模型权重：`/mnt/workspace/openvla-oft-ckpts`；
- 使用 OSMesa 进行无显示器渲染；
- 通过 `PYTHONPATH=/mnt/workspace/openvla-oft:/mnt/workspace/LIBERO:...` 暴露两个源码目录。

最终验证：

- `from libero.libero import benchmark` 成功；
- `libero_spatial` 共 10 个任务；
- 目标任务可读取 50 个初始状态；
- 基座模型能够正常加载、推理并保存 rollout MP4。

### 3.2 基座模型评估

先进行单状态冒烟测试，再完成 top drawer 50-state 扫描：

- 单状态冒烟成功；
- 50 个初始状态成功 48 个，失败 2 个；
- 失败状态为 state 29、state 32；
- 对 state 29 和 state 32 分别更换 5 个 seed 重测，均为 5/5 成功。

因此 state 29/32 在当前实例中不是稳定的确定性失败状态，而是低概率或对运行细节敏感的失败。

### 3.3 官方专家数据获取与校验

官方 LIBERO 数据下载期间多次遇到 Hugging Face 镜像超时。断点后确认当前已完整下载的目标 HDF5 文件可由 `h5py` 正常打开。

目标 top drawer 文件统计：

| 项目 | 结果 |
|---|---:|
| 专家轨迹 | 50 条 |
| 总 transition | 7479 |
| 单条长度 | 127～190 |
| 动作 | `(T, 7)` |
| agentview RGB | `(T, 128, 128, 3)` |
| wrist RGB | `(T, 128, 128, 3)` |
| proprio | `ee_states(6) + gripper_states(2)`，共 8 维 |
| simulator state | `(T, 92)` |

夹爪语义校验：

- HDF5 动作 `-1` 时，夹指状态接近张开；
- HDF5 动作 `+1` 时，夹指状态接近闭合；
- 因而官方 HDF5 原始标签中可确认 `-1=开、+1=关`。

### 3.4 HDF5 转换为 TFDS/RLDS

已完成 HDF5 → TFDS/RLDS 转换器和单任务数据注册：

- 数据集名：`libero_spatial_top_drawer`；
- 版本：`1.0.0`，另进行过夹爪符号试验版本；
- 训练集：50 episodes；
- TFRecord：8 shards；
- 生成规模约 639～640 MiB；
- 图像转换为 256×256；
- step 中保存 7D action、8D state、双路图像、语言指令和 RLDS 终止字段。

该阶段证明数据文件能够进入 OpenVLA-OFT 的 TFDS/RLDS 训练链路，但还不能仅凭“成功生成 TFRecord”证明所有动作语义和时间对齐都完全正确。

### 3.5 全量 LoRA 微调

主要配置：

| 参数 | 设置 |
|---|---|
| 数据 | top drawer 官方专家 50 条 |
| LoRA rank | 32 |
| 学习率 | `1e-5` |
| batch | 1 |
| 梯度累积 | 4 |
| 有效 batch | 4 |
| 训练步数 | 500 |
| 图像增强 | 开启 |

训练正常结束，最终记录约为：

- 总 loss：0.18701；
- 当前动作 L1：0.18335；
- 后续动作 L1：0.18762。

评估结果：

- Step 250 在目标状态失败；
- Step 500 在目标状态失败；
- 正确加载自定义统计量后仍失败；
- 夹爪动作翻转版本仍未得到改善；
- 保守训练方案仍未超过基座。

因此，本轮“单任务 50 条 + rank 32 + 500 steps”的全量 LoRA 配方未通过，不能部署。

### 3.6 head-only 微调

为隔离主干漂移，随后进行 head-only 实验：

- 从基座 action head 的 global step 150000 继续；
- 增训 200 个 step，终点显示为 150200；
- `150200` 是累计 global step，不是新训练了 150200 步；
- 冻结上游部分，主要更新 action head；
- 使用两种反归一化统计量分别评估。

严格 50-state 对照结果：

| 模型 | 成功数 | 成功率 | 失败状态 |
|---|---:|---:|---|
| 基座 | **48/50** | **96%** | 29、32 |
| head-only + 自定义统计 | 41/50 | 82% | 5、6、11、15、17、30、35、38、45 |
| head-only + 基座统计 | 37/50 | 74% | 3、5、6、10、11、28、29、33、36、38、40、42、44 |

重要更正：此前一度记录“head-only 48/50”，后续核对确认该结果来自切回基座模型后的评估，不应归属于 head-only。

共同对照状态 5、6、11、38 中，基座成功而两个 head-only 版本失败，说明 head-only 退化具有可重复的状态相关性，不是单次视频偶然现象。

## 四、诊断结果

### 4.1 上游编码器与 action head

同一指令、图像和 proprio 输入下：

- prompt 构造和 tokenizer 解码正确；
- 基座与 head-only 的 hidden state shape 均为 `(1, 56, 4096)`；
- hidden state 最大绝对差为 0；
- hidden state 平均绝对差为 0；
- 余弦相似度约 0.999988；
- 差异只出现在 action-head 输出。

这说明本轮 head-only 失败不能归因于视觉/语言上游被训练破坏。需要重点检查动作头输出、动作统计和闭环控制。

### 4.2 动作轨迹

动作 trace 已确认：

- 基座成功轨迹通常约 118～128 步结束；
- head-only 失败轨迹运行到 220 步上限；
- raw action 与进入环境的前 6 个动作维度一致；
- 第 7 维夹爪动作在进入环境前按评估器约定转换；
- head-only 的位置动作从早期 chunk 开始偏离，第二个平移维度尤为明显。

在 state 5、6、11、38 上，chunk 1～2 已出现持续位置偏移，之后才在 chunk 5～8 表现为抽屉接触、延迟碰碗或抓取失败。因此可见碰撞更像上游动作偏差积累后的结果，而不是故障起点。

### 4.3 open-loop 长度消融

对状态 5、6、11、38 分别测试 open-loop 1、4、8：

| open-loop steps | 成功数 |
|---:|---:|
| 1 | 0/4 |
| 4 | 0/4 |
| 8 | 2/4（state 5、6） |

缩短 open-loop 并未稳定改善，反而在这组样本上更差。因此不能把当前 head-only 失败简单归因于“8 步开环太长”。

### 4.4 MuJoCo 接触分析

对基座和 head-only 的 state 11、38 进行接触记录。

#### State 11

| 指标 | 基座 | head-only |
|---|---:|---:|
| 首次机器人—柜体接触 | step 55 | step 57 |
| 首次机器人—碗接触 | step 58 | step 65 |
| 柜体→碗时间差 | 3 步 | 8 步 |
| 柜体接触记录 | 9 | 9 |
| 柜体最深侵入 | 0.194 mm | 0.047 mm |
| 碗最深侵入 | 0.699 mm | 1.737 mm |

State 11 中 head-only 的柜体接触并不更深，却仍然失败。核心问题更可能是接触碗更晚、抓取中心偏移、双指包络失败、闭合时机错误或抬升动作不正确。

#### State 38

| 指标 | 基座 | head-only |
|---|---:|---:|
| 首次机器人—柜体接触 | step 58 | step 60 |
| 首次机器人—碗接触 | step 65 | step 74 |
| 柜体→碗时间差 | 7 步 | 14 步 |
| 柜体接触记录 | 5 | 14 |
| 柜体最深侵入 | 0.035 mm | 0.372 mm |
| 碗最深侵入 | 1.111 mm | 3.118 mm |

State 38 中 head-only 的柜体接触次数、侵入深度和碰碗延迟均明显恶化，说明错误接近几何在该状态中确实放大了失败。

综合结论：**基座成功时也可能先碰柜体，所以“是否碰柜体”不是有效的二元判据。应比较接触后的时序、双指抓取关系、碗是否抬升以及是否进入长时间卡住状态。**

## 五、遇到的问题与解决方案

| 阶段 | 问题/症状 | 根因 | 已采取或推荐的解决方案 | 状态 |
|---|---|---|---|---|
| 环境 | `ModuleNotFoundError: libero` | 新终端未恢复 venv/PYTHONPATH | 激活 `venv_oft`，加入 OpenVLA-OFT 与 LIBERO 源码路径 | 已解决 |
| 环境 | TensorFlow cuDNN/cuFFT/cuBLAS 重复注册警告 | TF/PyTorch 同进程加载插件 | 属于非致命日志；以实际 import、CUDA 和 rollout 为验收 | 已确认非主因 |
| 评估 | `--target_episodes` 不支持 | 当前评估器没有该参数 | 使用任务过滤与 `initial_state_offset`，或显式扩展评估器 | 已绕过 |
| 命令行 | `do`、括号、Python 代码被 Bash 当命令 | 复制了提示符、转义符或 Markdown | 只复制纯 Bash/Python heredoc，不复制提示符和代码围栏 | 已解决 |
| 下载 | Hugging Face 镜像超时 | 云端网络不稳定 | 断点续传；逐个 HDF5 用 `h5py` 校验完整性 | 部分数据已验证 |
| TFDS | 找不到版本或 `dataset_info.json` | 数据根目录多嵌套一层、使用了错误 data root | 以实际 builder_dir 为准，重新生成干净目录并验证 split | 已解决 |
| TFDS | dataset already registered | builder 被重复 import/注册 | 保留唯一注册入口，移除重复 builder import | 已解决 |
| 训练 | 评估全面失败 | 统计量键、动作语义、初始化和训练配方混杂 | 分别验证统计量、夹爪符号、模块加载；建立基座对照 | 已定位但模型未改善 |
| 训练 | 显示 150200 步 | resume 使用累计 global step | `150000 + 200 = 150200`，不是重新训练 150200 步 | 已解释 |
| 模型保存 | `No space left on device` | 多个合并模型各约 15 GiB，磁盘达 94% | 优先保留 adapter/head checkpoint；删除失败的半成品前先核对；必要时扩容 | 尚需持续管理 |
| 评估日志 | 终端无即时反馈 | 输出重定向到日志 | 使用 `tee` 同时显示并保存 | 已解决 |
| 动作 trace | `NameError: task_id` | `run_episode` 中使用未传入变量 | 显式传递任务/状态编号，或由调用层指定输出路径 | 已解决 |
| 接触分析 | 四组接触数均为 0 | JSON 接触记录存在嵌套，旧解析器只读最外层 | 使用递归解析器提取 geom/body 接触 | 已解决 |
| 抓取事件 | `num_steps: 0` | 采集 hook 插在未实际经过的 `env.step` 分支 | 将 hook 锚定到 `action_trace.append` 后的实际动作 `env.step` | 修复待验收 |
| 调试终端 | 终端异常退出 | 很可能继承了 `set -euo pipefail`，子进程非零导致 shell 一并退出 | 调试时关闭 `errexit/nounset`，保留 `pipefail`，读取 `PIPESTATUS[0]` | 待单组验证 |

## 六、已经排除或明显降级的解释

### 6.1 推理侧

当前证据已经排除或明显降低以下可能性：

- 指令文本错误或 prompt 不匹配；
- tokenizer 没有正确编码任务；
- head-only 训练修改了视觉/语言上游 hidden state；
- raw action 到 env action 的前 6 维发生额外变换；
- 仅把 open-loop 从 8 改为 1 或 4即可解决问题；
- 只要发生柜体接触就一定失败；
- state 29/32 在当前实例中是固定必败状态。

### 6.2 训练侧

以下方案在本轮条件下没有得到有效提升：

- 单任务官方 50 条数据直接进行 rank-32 LoRA；
- 仅选择 Step 250 或 Step 500；
- 只切换自定义统计量与基座统计量；
- 简单翻转夹爪标签；
- 只训练 action head；
- 继续选择累计 step 150200 的 head-only checkpoint；
- 通过缩短 open-loop 掩盖训练后动作偏移。

这些负结果只否定当前具体配方，不足以证明 LoRA 或 action-head 微调在所有设置下都不可用。

## 七、当前没有排除的根因

1. **抓取闭合时机错误**：夹爪可能在双指包住碗之前闭合。
2. **横向/高度对准偏差**：早期小偏移在狭窄抽屉中累积，导致手掌或单指先接触错误位置。
3. **单指推挤而非双指包络**：已有“碰到碗”的证据，但接触并不等同于稳定抓取。
4. **抓取后抬升方向错误**：碗可能被压住、推移或短暂弹起，没有形成持续抬升。
5. **训练 observation/action 时间错位**：RLDS 若存在一帧偏移，会显著破坏精细抓取。
6. **单任务数据分布过窄**：50 条轨迹足以验证管线，但可能不足以覆盖当前困难状态和保持原策略分布。
7. **action head 初始化或 resume 语义问题**：虽然已按 150000→150200 续训，仍需用训练前同输入零差异检查彻底验收加载链路。
8. **缺少基座数据 replay**：只使用单任务数据更新动作头可能造成遗忘和动作分布漂移。

## 九、下一步验证顺序

后续只做诊断，不立即继续训练：

1. 关闭 shell 的 `errexit/nounset`，对抓取事件记录器运行 **base state 11 单组冒烟测试**。
2. 验证输出 `num_steps > 0`，并确认 step 45～90 含末端位置、碗位置、夹指间距和接触标记。
3. 再运行 base/head-only × state 11/38 四组严格配对。
4. 提取事件时间线：首次闭合、左指碰碗、右指碰碗、双指同时接触、持续抬升 2 cm。
5. 根据结果分类：
   - 闭合早于双指接触：闭合时机/对准问题；
   - 只有单指接触：横向或姿态问题；
   - 双指接触但不抬升：夹持或抬升动作问题；
   - 碗抬升后掉落：闭合保持或后续轨迹问题；
   - 柜体接触后末端长时间停滞：碰撞约束/脱困问题。
6. 只有定位到明确可训练误差后，再决定是否制作混合数据集进行低学习率增训。

如果再次训练，建议最低约束为：

- 基座数据 replay 占 80%～90%；
- 目标专家数据占 10%～20%；
- 学习率 `1e-6～5e-6`；
- 保存 50/100/150/200 step 候选；
- 每个候选先做目标状态重复评估，再做 top drawer 50-state 回归；
- 任何候选低于基座 48/50，立即判定不通过。

## 十、当前决策

1. 正式实验和后续对照继续使用基座模型。
2. 全量 LoRA、head-only 自定义统计和 head-only 基座统计 checkpoint 均不用于部署。
3. 暂停增加训练步数；当前优先级是完成抓取事件闭环诊断。
4. 官方 50 条专家数据予以保留，但在完成 replay、时间对齐和初始状态覆盖验证前，不把它视为足以稳定增训的数据集。
5. 本轮最重要的成果不是得到新模型，而是建立了可信的权威基线，并把故障范围从“整个 VLA”收敛到“action head 输出—接近轨迹—抓取形成—抬升闭环”链路。
