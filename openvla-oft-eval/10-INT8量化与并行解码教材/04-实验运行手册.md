### 0.3 venv 解释器被换掉（实例重建后常见）

**症状**：

```
AssertionError: OpenVLA-OFT expects Python 3.10, found 3.12.13
```

同时 `bitsandbytes / transformers / flash_attn / libero / h5py / peft / draccus /
tensorflow / dlimp` 全部 `ModuleNotFoundError`，只剩 torch 与 numpy 能导入。
报错里若出现 **`No module named 'setuptools'`**，基本可确认是 Python 3.12
（3.12 起 venv 默认不装 setuptools）。

**原因**：DSW 实例**重建**后基础镜像的 python 版本变了（`dsw-2178764-*` →
`dsw-2179124-*`）。venv 在 NAS 上保留，但 `bin/python` 解析到新的基础解释器，
于是找不到原来 3.10 的 `site-packages`。

**先诊断（一条命令看全）**：

```bash
cat  /mnt/workspace/venv_oft/pyvenv.cfg
ls -l /mnt/workspace/venv_oft/bin/python*
ls   /mnt/workspace/venv_oft/lib/
which -a python3.10 python3.12 python3
ls -d /mnt/workspace/venv* 2>/dev/null
```

**分支 A0（最快，先试这个）：只把 `bin/python` 指回 3.10**

先看诊断输出里的两条：

```bash
# ① pyvenv.cfg 写着 version = 3.10.14，但 bin/python 是一个【间接】符号链接
venv_oft/bin/python -> /usr/local/bin/python
# ② lib/ 下同时有 python3.10 与 python3.12 两套 site-packages
ls venv_oft/lib/
```

**机理**：`bin/python` 指向的是基础镜像的 `/usr/local/bin/python`，而不是具体的
`python3.10` 二进制。实例重建后基础镜像的 `/usr/local/bin/python` 从 3.10 变成 3.12，
venv 解释器就跟着变成 3.12 —— 而 **site-packages 路径是由「运行中解释器的版本号」决定的，
不是由 `pyvenv.cfg` 的 `version` 字段决定的**。于是它去找几乎是空的
`lib/python3.12/site-packages`，3.10 的几百个包全部"消失"。

修复只需一条符号链接：

```bash
/usr/local/bin/python3.10 -V                       # 先确认这个二进制确实是 3.10.14
V=/mnt/workspace/venv_oft
echo "3.10 包数: $(ls $V/lib/python3.10/site-packages | wc -l)"   # 应为几百

ln -sfn /usr/local/bin/python3.10 $V/bin/python    # ← 唯一的一处改动

$V/bin/python -V
$V/bin/python -c "import torch,numpy,draccus,transformers,libero,robosuite,mujoco,gym; \
                  print('[OK]', torch.__version__, numpy.__version__)"
```

**不用重装 torch / flash-attn**。上面 8 个 import 全过即可继续跑实验。

**分支 A：`lib/python3.10/site-packages` 还在，且系统有 python3.10**

最省事——新建一个 3.10 venv，把旧 site-packages 挂进 `PYTHONPATH`，
**不必重装 torch / flash-attn**：

```bash
python3.10 -m venv /mnt/workspace/venv_oft310
source /mnt/workspace/venv_oft310/bin/activate

# 复用旧的 3.10 包目录（cp310 编译产物仍可加载）
export PYTHONPATH=/mnt/workspace/venv_oft/lib/python3.10/site-packages:$PYTHONPATH

python -c "import sys,torch,transformers,libero; print(sys.version.split()[0], torch.__version__)"
```

通过后把 `PYTHONPATH` 那行写进 `activate_oft.sh`（注意幂等）。

**分支 B：系统没有 python3.10，或旧 site-packages 已损坏**

只能重建环境（耗时较长，但确定性好）：

```bash
# 1) 装 python3.10（按镜像可用源，或 conda 建环境）
#    例：conda create -y -n oft310 python=3.10
#    或：apt-get install -y python3.10 python3.10-venv python3.10-dev

# 2) 用 3.10 重建 venv
python3.10 -m venv /mnt/workspace/venv_oft

# 3) 重新补依赖（工作区脚本，幂等）
bash setup_oft_env.sh
```

> **提示**：`setup_oft_env.sh` 会把包装进**当前激活的 venv**。
> 所以在跑它之前，务必先确认 `python -V` 是 3.10，否则装到 3.12 里白费功夫。

### 0.2 脚本退出码速查（别把语法错当成 OOM）

| 退出码 | 含义 | 排查 |
|---|---|---|
| **2** | **bash 语法/解析失败**，或脚本显式 `exit 2`（参数用错） | 见下 |
| 1 | 脚本通用失败 | 看日志里的 `[FAIL]` 行 |
| 126 | 不可执行（权限/格式） | `chmod +x`，或 `bash <脚本>` 而非 `./<脚本>` |
| 127 | 命令未找到 | 拼写或 PATH |
| 137 | 被 `SIGKILL`（128+9）—— **这才是 OOM/被 nohang 杀** | 见 §6 nohang 条目 |

**退出码 2 的两大常见原因**：

1. **换行符是 CRLF**（脚本从 Windows 侧编辑/复制/上传后被污染）。
   Linux 上 bash 把 `then\r` 当普通单词 → `syntax error near unexpected token` → 退 2。

   ```bash
   # 检查 + 一键修复（工作区提供）
   bash fix_crlf.sh --check
   bash fix_crlf.sh

   # 手工检查
   tr -cd '\r' < run_detached.sh | wc -c     # 非 0 就是有 CR
   ```

2. **参数用错**。本套脚本的参数错误都会 `exit 2`：

   ```bash
   bash run_detached.sh                      # 缺参数 → exit 2
   bash run_detached.sh diag_oom.sh          # 只给 1 个参数 → exit 2
   bash resume_verify.sh --bogus             # 未知参数 → exit 2
   ```

> **⚠️ 不要把长脚本整段粘贴进交互终端。** 尤其含 `exec > >(tee ...)`
> 这类进程替换的脚本，粘进终端会劫走整个会话的 stdout，表现为"终端异常退出"。
>
> **已确证的真实事故（2026-09-14）**：把 `run_detached.sh` 粘贴进终端执行，
> 其开头的参数检查 `if [ $# -lt 2 ]; then ... exit 2; fi` 因 `$#`=0 命中，
> **`exit 2` 关掉的是你的交互 shell 本身** —— 于是"终端异常退出，退出码 2"。
> 这不是 OOM，也不是环境问题。
>
> **正确姿势**：把脚本**上传成文件**（`oft_upload/oft_ops_scripts.zip`），
> 解压后 `chmod +x *.sh`，再 `bash 文件名` 执行。
> 本工作区所有含 `exit` 的脚本现在都有粘贴检测保护，但请勿依赖它。

**⚠️ 关键坑：不要设 `MODELSCOPE_ENDPOINT='https://mirrors.aliyun.com/modelscope/'`**

网上大量教程（包括不少 CSDN 高赞文）推荐这个环境变量，但它**只服务 `damo/`、`iic/`
这类官方模型**。对社区用户上传的模型（如本项目的
`a11111ad/openvla-7b-oft-finetuned-libero-spatial`）会直接返回 HTML 404：

```
[E3020] [404] <!DOCTYPE html> ... <h3>Ali-OSM</h3>
Request: GET https://mirrors.aliyun.com/modelscope/api/v1/models/a11111ad/...  ← 404
```

正确做法是**清掉该变量、走官方站点**（`download_oft_ckpt.sh` 已内联 `unset`）：

```bash
unset MODELSCOPE_ENDPOINT MODELSCOPE_CACHE
```

### nohang 的真实阈值（配置实测）

`/etc/dsw/cache/pre-install/plugins/nohang/v0.1.0/pai-nohang.conf`：

```
kill_process_group_enabled = True    ← 硬动作杀【整个进程组】
psi_checking_enabled = True
psi_path = /proc/pressure/memory     ← ⚠️ 本容器无此文件，PSI 判据失效
warning_threshold_min_mem = 40 %
soft_threshold_min_mem    = 3  %
hard_threshold_min_mem    = 2  %
soft_threshold_min_swap   = 10 %
hard_threshold_min_swap   = 4  %
print_mem_check_results = True
```

换算成绝对值（总内存 28 GiB）：

| 水位 | 空闲内存 | 行为 |
|---|---|---|
| 40% | 11.2 GiB | 只发警告 |
| **3%** | **~860 MiB** | **软动作**（限流） |
| **2%** | **~573 MiB** | **硬动作 → 杀整个进程组** |

因为 PSI 文件缺失，nohang 实际**只按内存百分比**判断。
它的日志不在 `/var/log/nohang/`、journalctl 也 grep 不到；
可从进程的 stdout 定位：`ls -l /proc/438/fd/1`。

> **跑基准前务必先补 swap 并开哨兵**：
> `bash setup_swap.sh` + `bash memwatch.sh &`

**`nohang` 是什么**：DSW 镜像预装的 OOM 预防守护进程，配置在
`/etc/dsw/cache/pre-install/plugins/nohang/*/pai-nohang.conf`，以
`nohang -c ... --monitor` 常驻。它在内存压力升高时**主动杀掉最耗内存的进程**
来保护整机 —— 所以：

- 症状是"终端/进程突然消失"，但 **`dmesg` 里查不到 `killed process`**（内核没参与）
- 这就是为什么加 sudo 读 dmesg 也找不到线索

**加 swap 的正确姿势（一键，已踩平 overlayfs 陷阱）**

```bash
bash setup_swap.sh --check     # 只探测哪个目录能放 swapfile，不实际启用
bash setup_swap.sh             # 实际创建（默认 32G）
SWAP_GB=16 bash setup_swap.sh  # 指定大小
```

**⚠️ 最大的坑：`/` 是 overlayfs，`swapon` 在其上通常会失败**

报错形如 `swapon: /swapfile: Invalid argument` 或 `swapfile has holes`。
`setup_swap.sh` 的处理方式：

1. 遍历 `/tmp /var/tmp /root /opt /home` 等，**打印各自 fs 类型**，
   排除 overlayfs / tmpfs / 网络盘；
2. 用 **64 MiB 小文件试挂**验证可行性，成功后才放大到目标大小；
3. 用 **`dd` 而非 `fallocate`** —— overlayfs 上 fallocate 易产生带洞文件，
   直接导致 `swapon` 失败；
4. 写 `/etc/fstab` 永久化；
5. 打印 nohang 三条阈值线与当前余量。

**实测可用落点**：`/tmp` 挂在 `/dev/vda3`（真实块设备，非 overlay），
磁盘 492G / 可用 392G，完全够用。

**手动兜底**（若脚本不可用）：

```bash
# 1) 先确认哪个目录不是 overlayfs
for d in /tmp /var/tmp /root; do printf '%s -> ' "$d"; stat -f -c %T "$d"; done

# 2) 在非 overlay 目录上用 dd 创建（32G）
dd if=/dev/zero of=/tmp/swapfile bs=1M count=32768 status=progress
chmod 600 /tmp/swapfile
mkswap /tmp/swapfile && swapon /tmp/swapfile
free -h

# 3) 永久化
grep -q '/tmp/swapfile' /etc/fstab || echo '/tmp/swapfile none swap sw 0 0' | tee -a /etc/fstab
```

**跑基准时同时开内存哨兵**：

```bash
bash memwatch.sh &     # 持续记录水位，越线时抓 top RSS
tail -f /mnt/workspace/_memwatch.log
```

> **绝不能把 swapfile 放 `/mnt/workspace`** —— 那是 NAS 挂载，
> swap 会慢到不可用甚至挂不上。
>
> **注意区分两类内存**：`nvidia-smi` 看的是**显存**（A10 24G），
> `free -h` 看的是**宿主内存**（28Gi）。两者独立。
