# 面试表达手册

## 1. 30 秒项目介绍

我做的是一个 C++17 数字人 SDK。它接收 TTS 的 16 kHz PCM 和头像，使用多线程 Pipeline 完成 Mel 特征、人脸检测与对齐、Wav2Lip ncnn 推理和口部融合，再把 BGR 与原始 PCM 编码成 H.264/AAC，支持 RTMP、RTSP 和文件输出。项目的重点不只是模型调用，而是实时流水线中的时间戳、反压、生命周期、错误传播和性能验证。

## 2. 90 秒项目介绍

项目分成四层：会话层调用外部 LLM/TTS 并做增量分句；核心层用 5 个 worker 和 7 级有界队列处理音频、人脸、匹配、推理和渲染；媒体桥把同一份 TTS PCM 一路送模型驱动口型，一路作为最终音轨；Publisher 用 FFmpeg 编码 H.264/AAC 并发布。

核心同步方式是由 25 FPS 左右的视频帧驱动 Matcher，根据视频 PTS 选择 `16 × 80` Mel 窗，每个视频帧只生成一个推理任务，避免 Mel 高频驱动造成任务放大。视觉侧使用 SCRFD、2D106 和 `96 × 96` 对齐，构造六通道人脸张量；模型输出通过逆仿射和 mask ROI 融合回原图。

工程上我重点关注有界队列、EOS 与 Stop 区分、线程回收、Pimpl/ABI、流式 HTTP、FFmpeg 时间基准和 profiler。当前项目仍有统一 MediaClock、打断 epoch、C API 输出和多会话共享调度等改进项，我会把这些作为下一阶段而不是已完成功能。

## 3. 三分钟回答结构

按以下顺序展开：

1. 业务目标：PCM + 头像 → 口型视频/直播流；
2. 系统边界：LLM/TTS 外部服务，SDK 负责本地媒体和推理；
3. 架构：四层、5 worker、7 队列、完整会话约 11 线程；
4. 算法链：Mel、人脸对齐、Wav2Lip、mask 融合；
5. 难点：时间线、反压、EOS、线程关闭；
6. 案例：一个真实 Bug 或性能定位；
7. 结果：用测试和指标描述，不只说“修好了”；
8. 边界：指出当前不足和下一步。

## 4. 三个推荐 STAR 案例

### 案例 A：口型不随语音变化

- Situation：视频能生成，但不同语音的嘴型响应弱。
- Task：判断问题在音频、预处理、张量还是模型。
- Action：固定 face 做不同 audio A/B，逐层检查 PCM、Mel、shape、值域和 blob，定位训练预处理契约不一致。
- Result：修正预处理并增加数值与响应回归；同时明确模型权重仍需独立验证。

重点体现：数值调试、对照实验、不能凭推理成功判断模型正确。

### 案例 B：短音频没有视频尾帧

- Situation：短 TTS 有音频输出但缺视频。
- Task：定位异步流水线的完成条件。
- Action：关联各队列和 EOS，发现瞬时空队列被误认为全部完成；改为显式 EOS 传播和下游确认。
- Result：短回复稳定输出，并新增短输入、在途任务和尾帧回归。

重点体现：并发完成协议、happens-before、回归测试。

### 案例 C：CPU 高但吞吐不高

- Situation：CPU 占用高，输出帧率没有同步提升。
- Task：区分有效推理和线程运行时开销。
- Action：用 perf 按 DSO 和 symbol 聚合，定位 libgomp barrier 自旋，再检查 worker、OpenMP 和 ncnn 线程预算。
- Result：历史环境中 busy wait 显著下降；保留同一输入 A/B 和质量检查。

重点体现：测量方法、线程过度订阅、不能把历史数据当当前基线。

## 6. 高频问题与回答要点

### 为什么选择 C++？

核心链路需要可控线程、内存、FFmpeg/ncnn/OpenCV 互操作、C ABI 和端侧部署。外围 LLM/TTS 服务仍可以用 Python，不应为了语言统一牺牲媒体核心效率。

### 为什么选择 ncnn？

端侧部署轻量、CPU 与 Vulkan 后端统一、依赖相对小，适合 C++ SDK。取舍是算子生态和调试工具不如部分云端框架丰富，模型转换和 blob 契约需要严格验证。

### 为什么使用有界队列？

无界队列会把吞吐不足转化为内存和延迟无限增长。有界队列迫使系统明确阻塞、丢弃或失败策略，并提供瓶颈观测点。

### 为什么 Matcher 由视频驱动？

输出目标由视频帧率决定。视频驱动保证每个显示帧最多一个推理任务，按 PTS 选择所需 Mel 上下文，避免高频 Mel 造成任务放大。

### 怎样处理音画同步？

`AVSync` 用音频主时钟：`audio_clock_ms = 累计消耗样本数 / sample_rate × 1000`，`drift = video_pts - audio_clock`，默认同步阈值 30 ms、严重漂移 100 ms；视频超前则等待/重复上一帧，视频滞后则丢帧追赶，严重偏移直接丢弃。`RenderThread` 提供了 `SetAudioPlayer()` 用于接入设备播放时钟，但 Pipeline 目前没有注入，实际跑的是样本累计时钟。统一 MediaClock 和打断 epoch 仍未落地，应如实说明。

### 怎样保证不会死锁？

不持一个队列锁阻塞操作另一个队列；条件变量谓词包含停止状态；Stop 唤醒所有 not_empty/not_full；外部调用和用户回调放在锁外；所有等待共享绝对 deadline。还要用确定性测试和 TSan 验证，而不是只靠设计自证。

### 如果推理慢于目标帧率怎么办？

先验证任务是否放大和是否存在重试；然后测前处理、推理、后处理和队列驻留。实时场景按 deadline 丢弃过期视频任务；再考虑线程预算、缓存、Vulkan、量化和跨会话调度。

### 如何证明测试充分？

展示正常、边界、失败和生命周期四类矩阵；提供 unit、integration、model、network、fault、sanitizer 和 install-consumer 证据，同时说明仍未覆盖的真实环境。

### 如果重新设计会改什么？

引入 session actor、统一 MediaClock/epoch/cancel/deadline、共享推理调度器、不可变 buffer 和稳定 C ABI；先修正确性和门禁，再做量化和多会话优化。

## 7. 不要过度声称

避免以下说法：

- “Pipeline 有 7 个线程。”正确是 5 个 worker、7 级队列。
- “当前使用 dlib 人脸检测。”当前主链是 SCRFD + 2D106。
- “已经实现完整音频主时钟同步。”当前 Render 没有完整接入 AudioPlayer。
- “Pause 会冻结所有处理。”当前只改变状态。
- “ASR 和打断已经完整闭环。”接口存在，但 turn flush/epoch 仍需完善。
- “C API 已经可独立完成输出。”当前缺少完整输出帧接口。
- “当前测试全部通过。”构建、模型和资源已清理，本轮没有重新验证。
- “支持麦克风实时采集。”只有 PortAudio 播放器和无锁 RingBuffer，没有采集回调。
- “噪声环境下做过设备兼容验证。”缺少目标声卡与驱动的实测矩阵。
- “当前性能是某个历史 FPS。”旧报告必须注明硬件、提交和测量口径。

## 8. 简历描述原则

好的描述包含动作、难点和证据：

```text
设计 C++ 多阶段数字人口型流水线，以 5 个 worker 和有界队列隔离音频、视觉、推理和渲染抖动；建立 PTS/EOS/反压契约，并通过分段指标和故障测试验证。
```

不要写无法证明的绝对数字或“负责全部系统”。第三方库与个人工作要区分：可以说“基于 ncnn/FFmpeg 实现适配、调度和工程化”，不能把 ncnn 算子或 Wav2Lip 模型本身说成自研。
