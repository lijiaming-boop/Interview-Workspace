## 3. 所有 C++ 岗位都会问的基础问题

### Q1：为什么大量类使用 `std::unique_ptr<Impl>`？

参考答案：这是 Pimpl。公共头文件只暴露 `Impl` 前置声明，具体成员放进 `.cpp`，可以减少头文件依赖和增量编译范围，也能避免 FFmpeg、线程实现等私有类型泄漏到 SDK API。对于动态库，它还能降低私有成员变化造成的 C++ ABI 风险。代价是一次堆分配和一次间接访问，类的析构函数通常必须放在 `Impl` 完整可见的 `.cpp` 中定义。

追问：Pimpl 是否能保证完整 ABI 稳定？

回答：不能自动保证。虚表、编译器、标准库 ABI、异常、RTTI 和导出符号仍可能影响兼容性。因此项目同时提供 C API，使用固定宽度类型、显式 `struct_size` 和错误码作为更稳定的跨语言边界。

### Q2：为什么线程和队列禁止拷贝？

参考答案：线程、mutex、condition variable 和队列都代表唯一的同步状态或资源所有权，复制后无法定义两个对象应共同还是分别拥有底层线程。禁止拷贝可以让所有权清晰。部分无活动线程的包装类可以提供 move，但并发运行期间移动仍不安全，所以项目会限制使用场景。

### Q3：RAII 在项目中解决了什么问题？

参考答案：RAII 让线程、网络句柄、FFmpeg context、模型和动态对象的释放绑定到对象生命周期。正常返回、错误返回或异常路径都走析构，减少遗漏清理。需要注意：线程析构虽然可以 join，但不能只依赖析构；应先设置停止状态并唤醒阻塞点，再 join，否则析构可能永久阻塞。

### Q4：`std::move` 一定不发生拷贝吗？

参考答案：不一定。`std::move` 只是转成右值引用，最终调用 move 还是 copy 取决于类型是否有可访问的移动构造，以及对象是否为 const。对于 `cv::Mat`，移动或普通复制主要转移/增加引用计数，若跨线程需要独立像素所有权，应显式 `clone()`。

### Q5：为什么使用 `steady_clock` 做超时，而不是 `system_clock`？

参考答案：`steady_clock` 单调递增，不受系统时间校准或用户修改影响，适合 deadline、耗时和重试窗口。`system_clock` 适合墙上时间和日志，但时钟跳变会破坏超时判断。

### Q6：原子变量能不能替代 mutex？

参考答案：原子适合单个计数器、标志或可以用明确原子协议表达的状态转换。多个字段需要保持不变量时仍需 mutex。例如发布器的 `opened/closing/failed` 与队列操作需要在同一个临界区内一致变化；指标计数可以使用 atomic 降低竞争。

### Q7：为什么条件变量必须带谓词？

参考答案：条件变量允许虚假唤醒，而且被唤醒时条件可能已经被其他线程改变。正确形式是 `wait(lock, predicate)`，谓词同时检查“资源可用”与“正在停止”，这样 Stop 后 `notify_all` 才能让阻塞线程退出。

### Q8：如何保证异常不会让工作线程直接 `std::terminate`？

参考答案：线程入口最外层捕获 `std::exception` 和未知异常，将状态设置为 ERROR，记录日志并通知等待方。回调也要设置异常边界，因为用户回调不受 SDK 控制。不能让异常穿出 `std::thread` 的入口函数。

### Q9：为什么错误码和异常同时存在？

参考答案：SDK 公共边界和 C API 使用错误码，便于 ABI、跨语言和调用方显式处理；内部资源封装可以用异常表达构造或不可恢复失败，但必须在公共边界捕获并转换。实时数据路径倾向错误码，避免异常成本和不可预测控制流。

### Q10：怎样证明项目不是“能跑一次的 Demo”？

参考答案：给出三类证据：第一，生命周期和故障路径测试，如重复启动、超时停止、空输入和缺模型；第二，完整依赖与关闭可选依赖的构建矩阵；第三，指标和长稳数据，如 P95 推理耗时、队列峰值、丢帧、音画偏差、内存和重复启动次数。项目有前两类的历史验证记录，但资源清理后尚未重新构建复测；长稳和目标机器性能数据也仍需补测。

## 4. C++ 音视频/流媒体岗位

### 重点模块

- `include/media/stream_publisher.h`、`src/media/stream_publisher.cpp`
- `include/media/conversation_stream_bridge.h`
- `include/core/media_clock.h`
- `include/core/av_sync.h`
- `include/core/audio_sync_scheduler.h`
- `examples/publisher_resilience_test.cpp`

### Q1：从 PCM/BGR 到最终直播流经过哪些步骤？

参考答案：TTS 输出 float PCM，同时送入 SDK 做口型驱动和 Publisher 做音频编码。音频经 libswresample 转为编码器要求的采样率、声道布局和 sample format，再按 AAC frame size 送编码器。SDK 输出 BGR 帧，使用 libswscale 转成编码器要求的 YUV 像素格式，H.264 编码后和 AAC packet 按时间戳交错写入 FLV、RTMP 或 RTSP muxer。

### Q2：PTS、DTS 和 time base 是什么？

参考答案：PTS 表示呈现时间，DTS 表示解码时间；存在 B 帧重排时二者可能不同。time base 是时间戳单位，例如 `1/25` 或 `1/48000`。业务层使用毫秒输入，进入 FFmpeg 时必须用 `av_rescale_q` 转换到 stream 或 codec time base，写 muxer 前还要保证 packet 时间戳属于目标 stream 的 time base。

### Q3：为什么音频不能像视频一样随意丢？

参考答案：视频丢一帧通常表现为短暂卡顿，而音频丢样本会产生爆音、断裂，并改变后续时间轴。实时系统在拥塞时通常优先丢旧视频、保持音频连续；但音频也不能无限堆积，因此需要有界队列、最大保留时长和明确的 DROP/RETAIN/FAIL_SESSION 策略。

### Q4：如何处理音画不同步？

参考答案：先统一时间基准，以音频样本数建立相对稳定的主时钟，视频帧携带 PTS。匹配阶段计算音视频偏差，在阈值内配对；视频落后严重时可丢帧，超前时等待或帧调度。项目暴露 drift、匹配误差、丢帧和队列深度指标。不能只看当前队列是否为空判断 EOS，因为上游线程可能仍在处理已取出的数据。

### Q5：FFmpeg 编码结束为什么要 flush？

参考答案：编码器内部可能缓存 B 帧或不足一帧的音频数据。结束时向编码器发送空 frame，并持续 receive packet，直到 EOF；重采样器的残留和 FIFO 也需排空，最后写 trailer。否则容易丢失尾部音视频或生成不完整容器。

### Q6：推流断线重连应该怎样设计？

参考答案：写包失败后先进入 reconnecting 状态，阻止无限积压；清理旧 muxer/IO context，按指数退避在总重连窗口内重新初始化输出。视频通常清空旧帧并等待关键帧，音频按策略丢弃、有限保留或直接失败。Close 必须能打断 backoff 和 IO，且“用户主动关闭”不能被记录成网络失败。重连测试需要真实 RTMP/RTSP 服务或可控代理，离线文件故障注入只能覆盖状态机的一部分。

### Q7：为什么 RTMP、RTSP 和 FILE 的队列策略可能不同？

参考答案：文件输出关注完整性，可以允许生产者适度等待；直播关注低延迟，旧视频即使编码出来也失去价值，因此更适合丢旧帧。网络协议还面临断线、服务端背压和 IO 超时，需要限制队列对应的最大媒体时长，而不能只限制元素个数。

### 岗位加分准备

- 能用 `ffprobe` 解释输出 stream、codec、time base 和 packet。
- 准备一次 RTMP/RTSP 断线恢复录屏及指标变化。
- 补测首包延迟、P95 编码耗时、最大音画偏差和丢帧率。

## 5. C++ AI 推理/端侧部署岗位

### 重点模块

- `model/model_loader`、`model/model_inferencer`
- `model/output_processor`
- `core/inference_worker`
- `audio/audio_mel_feature_extract`
- `core/face_detector`、`face_aligner`

### Q1：Wav2Lip 的输入输出是什么？

参考答案：音频侧将 PCM 转为 Mel 特征窗口；视觉侧检测和对齐人脸，构造模型要求的人脸张量。模型输出合成的人脸区域，再由 OutputProcessor 恢复到图像空间并与原始头像融合。面试时应结合当前模型实际 tensor 名称、NCHW/维度和归一化参数说明，不能只回答“输入音频和图片”。

### Q2：为什么模型加载和推理要分离？

参考答案：加载包含磁盘 IO、参数解析、权重上传和 warmup，成本高且只应在初始化阶段发生；推理是高频实时路径。分离后可以在 Start 前验证模型，避免工作线程启动后才发现权重缺失，也便于统计 IO、warmup 和单次推理耗时。

### Q3：warmup 有什么作用？

参考答案：首次推理可能触发内存分配、算子 pipeline 创建、GPU shader 编译和缓存建立，明显慢于稳态。用真实形状的零输入 warmup 可以提前完成这些工作，让首帧延迟更稳定。但 warmup 成功不等于精度正确，还需要固定样本做输出一致性验证。

### Q4：为什么推理独立线程，而不是调用方同步执行？

参考答案：音频预处理、视频预处理、推理和渲染耗时不同。独立线程和有界队列可以流水并行、隔离抖动，并对每阶段采集耗时。代价是需要处理反压、帧所有权、EOS 和队列延迟，线程数也不是越多越好，OpenCV、OpenMP 和 ncnn 可能争抢同一批 CPU 核。

### Q5：CPU/GPU 如何选择和验证？

参考答案：目标设计应使用 `Auto/CPU/Vulkan` 等显式后端，在加载模型前完成能力检测，并报告实际选择和回退原因；不能只看“设备存在”，应运行真实模型并确认输出有效。当前实现存在配置一致性缺陷：SDK 默认 `enable_gpu=false`，但底层 inferencer 默认 `use_gpu=true`，默认配置未必可靠禁用 Vulkan。性能比较需要固定输入、预热、多次采样，报告 median/P95，而不是只取最快一次。

### Q6：如何定位推理性能瓶颈？

参考答案：先分段测量人脸检测、对齐、Mel、tensor 转换、Infer 和后处理；再观察队列峰值确定瓶颈阶段。使用 profiler 区分计算、内存拷贝和线程争用。若推理快但输出 FPS 低，问题可能在前后处理或调度；若增加 ncnn 线程反而变慢，通常是与 OpenMP/OpenCV 过度订阅。

### Q7：量化模型上线前要验证什么？

参考答案：需要代表性校准集、输入预处理完全一致、逐层或端到端误差、口型质量指标、速度、内存和目标硬件兼容性。项目支持导出真实 Wav2Lip 输入用于 INT8 校准，但没有真实精度报告前不能声称量化无损。

### 岗位加分准备

- 熟记当前模型输入输出 tensor 名称、维度和归一化。
- 展示 CPU/GPU 的 warmup、median、P95、FPS 和内存对比。
- 准备一例“线程数增加但性能下降”的分析。

## 6. C++ SDK/客户端基础架构岗位

### 重点模块

- `include/digital_human_sdk.h`、`include/digital_human/c_api.h`
- `core/sdk_entry`、`core/c_api`
- `core/thread_base`、`worker_registry`、`thread_safe_queue`
- `digital_human/error`、logger、metrics、quality_gate
- 根 CMake、`src/CMakeLists.txt`、`tests/CMakeLists.txt`

### Q1：SDK 生命周期为什么设计成状态机？

参考答案：Init、Start、Pause、Resume、Stop 对资源要求不同。如果只用多个 bool，很容易出现互相矛盾的组合。项目使用单一 SDKState，并在 lifecycle mutex 下检查和迁移，从而明确非法调用，例如未初始化 Start、运行中重复 Init、Stop 后重新启动。目前 STOPPED 是终态，这是一种简化资源重建语义的明确选择。

### Q2：为什么启动线程要从下游到上游，停止时反过来处理？

参考答案：启动下游优先可以保证上游一产生数据就有消费者；停止需要先停止输入并传播 EOS/停止信号，再唤醒所有队列，最后等待线程退出。若先销毁下游，上游仍可能向已销毁资源写入；若只设置 flag 不唤醒条件变量，线程可能永远阻塞。

### Q3：`ThreadBase::Wait(timeout)` 超时后为什么不能 detach？

参考答案：detach 后对象可能析构，而线程仍访问 `this` 和成员，造成 use-after-free。当前设计超时只返回 false，线程仍由对象持有，后续可以再次 Wait；调用方必须继续保留对象并完成协作式停止。C++ 标准线程没有安全的强制终止，因此 Run 中的每个阻塞点都必须可取消。

### Q4：C API 的 `struct_size` 有什么用？

参考答案：`struct_size` 的目标设计是让调用方填写自己知道的结构大小，库按可用前缀读取，并为新增尾部字段使用默认值，从而支持向后扩展。但当前实现直接要求大小不小于当前完整结构，尚未实现前缀兼容。改进时应按 `offsetof` 检查最小必需前缀，并配合 API version、固定宽度类型和清晰的字段所有权。

### Q5：如何设计 SDK 回调的线程语义？

参考答案：必须文档化回调在哪个线程触发、是否串行、能否重入 SDK、参数的生命周期和回调耗时限制。对 `cv::Mat` 等引用计数对象，要说明回调返回后是否仍有效；如果调用方要异步保存，应 clone。SDK 应捕获用户回调异常，并避免持有内部 mutex 时调用外部回调，防止重入死锁。

### Q6：可选依赖裁剪是怎样实现的？

参考答案：HTTP、媒体、PortAudio 和音频文件加载分别由 CMake option 控制，源码目标按条件加入，公共 facade 不应无条件链接可选库。测试也按 `dh_network`、`dh_media` 目标是否存在来注册。验证时同时构建完整依赖和关闭可选依赖的最小配置。

### Q7：如何保持公共 API 稳定？

参考答案：控制导出符号，Pimpl 隐藏实现，避免公共头暴露第三方类型，新增字段尽量放结构体尾部，错误码只追加不重排；C API 使用版本和 size。发布前用 ABI 检查工具比较符号，并保留兼容性测试。项目当前仍在快速演进阶段，完整 ABI 门禁是后续项。

### 岗位加分准备

- 能画出 Init/Start/Pause/Resume/Stop 状态迁移图。
- 准备一个 shutdown timeout 的复现与修复。
- 增加 install 后由外部小项目 `find_package` 的消费者测试。

- metrics、logger、quality gate

### Q1：为什么队列必须有界？

参考答案：生产速度长期高于消费速度时，无界队列只会把延迟问题转化为内存耗尽。有界队列使反压显式化，可以阻塞、丢弃或失败，并通过容量和峰值指标定位瓶颈。容量应按可接受媒体时长和阶段抖动确定，而不是随意取一个大数。

### Q2：阻塞 Push 和 TryPush 怎么选择？

参考答案：不能丢的数据或文件处理可阻塞 Push，但必须能被 Stop 唤醒并设置超时；直播视频适合 TryPush 或丢旧帧，避免延迟不断增长。策略取决于数据价值，不能为所有队列统一使用一种行为。

### Q3：如何避免队列死锁？

参考答案：不在持有一个队列锁时阻塞操作另一个队列；条件变量谓词包含 stopped；Stop 设置状态后对 not_empty/not_full 全部 `notify_all`；复杂停止由统一 WorkerRegistry 编排。多 mutex 同时加锁时用 `std::lock`/`scoped_lock` 保证一致顺序。

### Q4：HTTP 客户端需要哪些生产级边界？

参考答案：连接超时、总请求超时、低速超时、响应体上限、取消检查、状态码、Content-Type 校验、重定向策略和错误信息。TTS 特别需要边收边解析，不能先把整段响应无界缓存；响应字节和最大音频时长要双重限制。

### Q5：SSE 为什么要处理分片？

参考答案：一次 socket/write callback 不对应一条 SSE event，行可能被拆成多块或多行合并到一块。客户端需要保留 line buffer，按换行增量解析 `data:`，处理 `[DONE]`，并正确处理取消和最后一行没有换行的情况。

### Q6：如何做可观测性？

参考答案：日志用于离散事件并携带 session/turn 上下文；metrics 用于聚合趋势，包括请求数、错误、阶段耗时、队列深度、丢帧和重连；QualityGate 将指标转成自动验收结论。高频路径避免每帧 INFO 日志，耗时需要直方图或分位数，而不仅是平均值。

### Q7：平均耗时为什么可能误导？

参考答案：实时系统经常是长尾影响体验，少量严重卡顿可能被平均值掩盖。因此至少报告 median、P95/P99、最大值和样本量，并关联队列深度。如果只是把所有样本永久保存计算分位数，还需考虑观测本身的内存成本，可使用滑动窗口或近似直方图。

### 岗位加分准备

- 用压测制造生产快于消费，展示反压和内存稳定。
- 使用 ASan/UBSan/TSan 或 Valgrind 给出报告。
- 能解释取消、deadline 传播和幂等 Stop。

## 8. 计算机视觉/C++ 图像处理岗位

### 重点模块

- `avatar/avatar_image`
- `core/image_loader`
- `core/face_detector`、`face_aligner`
- `core/face_mask_generator`
- `model/output_processor`

### Q1：为什么头像上传不能直接 `imdecode` 后使用？

参考答案：上传内容不可信，需要先限制编码字节数、校验 JPEG/PNG 魔数和 Content-Type，再读取宽高并限制像素数量，防止解码炸弹和超大内存。解码后统一转换为 BGR，并确保最终 Mat 独立拥有内存。

### Q2：`cv::Mat` 的浅拷贝有什么风险？

参考答案：`cv::Mat` 复制通常共享引用计数像素。跨线程或保存用户上传帧时，调用方可能修改原 Mat，或者外部 buffer 生命周期结束。需要明确只读契约，或在边界 `clone()` 获取独立存储。clone 会增加带宽和内存成本，因此不是所有内部传递都无条件复制。

### Q3：为什么人脸需要对齐？

参考答案：检测框只提供大致区域，不同姿态、尺度和旋转会让嘴部位置变化。通过关键点和仿射变换把人脸映射到模型训练时的标准坐标，可以降低输入分布偏差，使口型区域更稳定。输出后再用逆变换放回原图。

### Q4：图像融合为什么需要 mask？

参考答案：直接覆盖模型输出 ROI 会产生明显矩形边界、颜色和纹理突变。mask 控制主要替换嘴部区域，并通过羽化使边缘平滑。需要处理 ROI 越界、mask 尺寸、通道、数值范围以及不同脸部尺度。

### Q5：BGR、RGB 和 YUV 的区别是什么？

参考答案：OpenCV 默认 BGR，许多模型训练输入是 RGB，而视频编码器通常使用 YUV420P/NV12。转换时不仅是通道顺序，还涉及色彩矩阵、范围和 chroma subsampling。若颜色异常，应逐段确认格式、stride、range 和颜色空间，而不是只交换 R/B。

### Q6：奇数分辨率为什么可能导致编码失败？

参考答案：YUV420 色度平面在宽高方向都是 2:1 采样，编码器通常要求偶数宽高。项目在初始头像阶段把画布归一化为偶数尺寸，后续热更新头像缩放到固定画布，避免编码过程中改变分辨率。

### 岗位加分准备

- 展示检测框、关键点、对齐图、mask 和最终融合的可视化。
- 准备错误案例：侧脸、遮挡、多人脸、超小脸。
- 给出每阶段耗时和图像 clone 次数分析。

## 9. 面试官最可能针对本项目追问的问题

### Q1：这个项目最大的技术难点是什么？

参考答案：不要回答“接入了很多库”。可以回答多阶段异步流水线的完成语义：上游输入 EOS 不代表下游已经处理完，曾经短音频场景因瞬时队列为空而提前结束，导致只有音频没有视频。修复方式是让每阶段显式传播 EOS，并增加短回复回归测试。这个回答同时体现并发、定位和验证。

### Q2：你亲自修复过什么 bug？

可选择真实案例：

1. VAD Stop 后重启没有清理 residual samples，上一会话尾部会污染下一会话；通过重启隔离测试复现，在 Start 时清零。
2. 工作线程 Wait 超时后不能 detach，否则对象析构会导致 use-after-free；改为保留线程所有权并允许再次 Wait。
3. 短回复场景错误推断视频处理完成；改为显式 EOS 传播。

回答结构统一为：现象 → 最小复现 → 根因 → 修改 → 回归测试 → 是否仍有边界。

### Q3：为什么不直接用 Python 实现？

参考答案：LLM/TTS 服务本身可以用 Python，但本项目重点是本地实时媒体与推理 SDK：需要可控的线程、内存、FFmpeg 编码、低延迟数据传递、C ABI 和端侧部署。C++ 更适合这些核心路径；外围服务仍可以选择 Python，系统不应为了语言统一而牺牲适配效率。

### Q4：项目目前最不足的地方是什么？

参考答案：真实网络重连和长稳验证仍不充分，尚未形成统一的一键演示和目标硬件性能报告；当前是单机终端多轮会话，不是多租户生产服务。下一步优先做 RTMP/RTSP 可控故障测试、ASan/TSan、两小时长稳和首帧/P95 延迟报告，而不是继续增加表面功能。

### Q5：如果再给两周，你会做什么？

参考答案：第一周完善可靠性：修复重连边界、增加代理故障注入、Sanitizer 和 CI；第二周完善交付证据：一键启动、演示录屏、CPU/GPU 性能矩阵和火焰图。Web UI/ASR 可以作为后续产品层，不优先于核心稳定性。
